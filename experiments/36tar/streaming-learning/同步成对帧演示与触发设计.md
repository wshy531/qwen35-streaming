# 同步成对帧演示与触发：下一步设计

2026-10-10。本文保存实施前的原始候选设计；实施预登记和固定运行事实分别见同步成对帧演示验收方案.md、同步成对帧演示结果与复现.md，进度唯一主记录为实验总纲。基于在线同四帧Q1正例和已有容量/奇帧接口，把可验证状态协议变成小型同步演示。引用流式调研的“观察和回答分开”思想，不称已实现StreamMind学习门控。

## 候选行为

| 情况 | 预定行为 |
|---|---|
| 顺序读取视频 | 1FPS保留真实PTS，最长边256，固定192×256画布；只有已交付采样帧进入模型 |
| 一帧待配对 | 只保留该帧，不做视觉/语言计算，不提问 |
| 到齐下一帧 | 新两帧单独编码并续接主四状态；完成后释放原RGB |
| 本次reset后不足4个真实帧 | 演示不触发首问；底层两帧ask功能不改，只在演示层选择等待 |
| 达到4个真实帧 | 问固定主体Q1，从fork分支生成，返回截止时间/答案/状态长度 |
| 首问后再来2个真实帧 | 再触发同题，问答仍不回写主视频历史 |
| 新一对会超主Token预算 | 在GPU前显式reset；保存当前两帧，再按原ID/PTS投入新epoch，重新积累首问上下文；记录历史被放弃 |
| EOF剩一个真实帧 | 明确记录合成末帧副本，真实计数不增加；不足首问条件就不问。若补齐也超容量，先记录reset后处理，不静默吞帧或补造未来 |
| 用户结束/异常 | 关闭reader/session，保留当前小JSON与失败记录；无法恢复的session需reset，不承诺并发或回滚 |

容量不能按“永远6帧”写死：时间戳字符串长度会变化，必须按新块实际Token加prefix/问题/答案预留检查；默认单序列256、主预算176。接收阶段和模型已编码阶段分别计数。应用只暂存最多两张RGB，并按对预检，避免容量reset时丢掉已等待的第一帧。

这是有界的一段持续历史，在epoch内保留所有实际主Token；不冒称固定四帧滑窗或长期记忆。reset清空历史，不能回答已丢弃epoch的事件。四帧首问只依据本片段，仍需其他视频验证；更多上下文不保证计数/顺序正确。

## 实施前必须通过

先用CPU/微型模型验证：四帧前不问、4/6帧触发截止正确、问题不进主缓存；准确Token容量预检在GPU前执行，当前新两帧跨reset不丢；奇帧真实计数/补齐/触发一致，关闭和异常记录完备。源码/视频/SHA冻结后，再登记有限文件重放的采样数/问答数/reset数/forward和生成上限/显存/墙钟时间，不能复用其他实验的预检。

初步展示形式为顺序事件日志：已到达时刻、等待/编码/提问/reset、模型答案、主状态Token数及问答耗时。实时速度、摄像头、异步队列、长期压力后续各自预算，本步骤不自动下载/训练、Token压缩/森林或裁剪KV。先前BF16续接与不同视觉编码的严格失败仍保留。
