# S2：顺序视频输入与近期滑窗

进度唯一来源为 `实验总纲.md`。本文件定义实现与验收，不把设计当作运行结果。

## 做什么

```text
顺序取得一帧及其 PTS → 因果采样 → 最近 4 帧缓冲
                                    ↓ 每 2 个采样帧触发
          当前窗口 + 实际时间戳 + 当前问题 → 原模型独立生成 → 记录并释放
                                    ↓
                         再取得下一帧
```

默认 1 FPS、窗口 4 帧、每 2 个采样帧回答一次。窗口不足 4 帧时使用已经到达的帧；不会为了凑满窗口提前取得后面的帧。视频末尾不足触发间隔时不自动补一次问答，单帧/奇数帧路径通过单独 CPU 预检验证。

这实现应用层在线视频窗口，不续接跨窗口 KV 或递归状态；每次重新编码当前窗口，问答之间清除 rope_deltas 并从空语言缓存开始。生成内部仍使用原生单 Token 缓存。自然视频、摄像头、异步队列与长运行界面是后续工作，本阶段先用可复查的同步文件重放。

## 时间与输入

采样只根据已经交付的帧 PTS，不能按全视频长度做 linspace。PTS 减去首帧 PTS，得到视频开始以来的秒数；窗口滑动后不归零。拒绝缺少 PTS、时间倒退/重复或非法 RGB 输入，不静默捏造时间。

处理器正常的视频路径用 frame_index/fps 计算时间；对于按 PTS 选出的窗口，我们单独调用同版本 video_processor，然后按同版本格式插入两帧时间块的平均 PTS。模板、视觉占位符、mm_token_type_ids、grid 与位置适配保持原格式，CPU 以规则时间帧与完整 processor 输出逐张量比较。不修改 site-packages 或原模型。

若帧数为奇数，沿用原处理器复制末帧完成 temporal_patch_size=2；时间也复制已知末帧。不读取未来帧补齐。检查实际视觉 Token 数、显式位置、时间块数量与最大输入预算。

框架/解码器可能在内部缓冲压缩包或未来参考帧；本阶段保证的是应用交付和模型输入没有超过回答截至时刻的帧，不宣称底层编解码器完全没有内部预读。文件重放按视频时序前进，没有实时等待，耗时与时间戳不是同一个概念。

## 状态和有界性

- 窗口只保留最多 4 份缩小到最长边 256 的 RGB uint8 像素；每帧复制且只读，避免调用方后改像素影响旧窗口。
- 帧编号和时间严格递增；先验证，再提交。非法输入不能改变窗口。
- reset 清除窗口、计数、最后编号和时间；不同视频分别 reset。
- 每次问答记录窗口帧编号/时间/像素哈希、已交付帧计数、Token/输入指纹、完整答案、耗时和显存。
- 同步流程没有后台解码生产者或无上限队列。资源记录仍要区分窗口像素字节、processor 临时张量、生成缓存和 PyTorch 显存；不能用 4 帧上限推断系统 RAM 全部有界。

## 验收

1. 带访问记录的帧生成器证明问答触发时只取到当前帧；同前缀不同后缀在分叉前的窗口/模型输入完全相同。
2. 时长、采样率与掉帧测试；非均匀 PTS 只影响已知时间；重复/倒退输入拒绝且不改状态。
3. 到第 6 帧窗口为帧 2–5，第 8 帧为 4–7；像素缓冲不超过 4 帧；reset 与新实例状态一致。
4. CPU 实际 MP4 路径与处理器等价；1/2/3/4 帧路径通过、时间戳不随窗口归零、补帧不引入新编号。
5. 两条 12 帧合成视频，开头同为红色，后面分别改变为蓝/绿等颜色；每 2 帧问当前窗口末帧颜色。12 次答案人工核对，前缀答案一致；它只证明这些合成输入的简单当前颜色能力。
6. 记录每次问答的原视觉前向调用和语言首轮 past 长度，确认窗口之间没有缓存串用；分开测 CPU 解码/处理、输入传输、视觉区间、语言 prefill/decode 与整次生成。

首次 GPU 上限：单卡、BF16、最多 4 个 256×256 采样帧/次、最多 1024 输入 Token/次、16 输出 Token/次、12 次问答、总进程 600 秒。必须先通过 CPU 测试和接口预检；不训练、不启用任何压缩机制。
