# qwen35-streaming：架构与计划解读

审阅日期：2026-10-09（Asia/Shanghai）。
审阅对象：[wshy531/qwen35-streaming](https://github.com/wshy531/qwen35-streaming)。

## 1. 先给结论

这是一个以 **Qwen3.5-0.8B 官方权重**为起点、逐步改成流式视频理解系统的合作项目。当前已建立“可独立修改、可与上游比较的模型源码基线”，流式视频输入、缓存裁剪和 SFT 都未实现。仓库 README 明确承认这一点。

用户已决定后续按这个合作方案推进，因此之前的 LLaVA 最小方案转为历史参考。我们保留因果性、reset、容量和问答隔离等通用验收思想，但不会将 LLaVA 的预处理格式、依赖版本或 KV-only 状态假设直接移植到 Qwen3.5。

阅读范围：仓库全目录、README、依赖、来源记录、smoke 脚本、三项测试、配置源码；模型源码中的视觉编码、特征拼接、Gated DeltaNet、普通注意力、缓存、位置构造及生成入口。模型约 10 万字节，未把每个通用数学 helper 都逐行讲解，也没有执行远端代码或重新运行其测试。

## 2. 这个仓库为何复制模型源码，而不是只写调用脚本

`qwen35_local` 相当于把要改造的机器核心搬到自己的工作台：视觉模块、语言层、缓存和配置都能在这里修改；加载、生成、处理器等通用设施仍复用固定版本的 Transformers。

| 文件 | 作用 | 以后在哪里动手 |
|---|---|---|
| `qwen35_local/configuration_qwen3_5.py` | 模型各模块尺寸、层型及位置配置 | 阅读真实配置；新增参数必须与 checkpoint 兼容 |
| `qwen35_local/modeling_qwen3_5.py` | 视觉、混合语言层、缓存、多模态拼接与输出 | 核心架构改造 |
| `scripts/smoke_test.py` | 官方权重文字/单图加载验证 | 后续扩展短视频与机制 smoke |
| `tests/test_local_model.py` | 微型随机网络与上游实现比较 | 加入多 token chunk、状态隔离和 reset 检查 |
| `third_party/upstream.json` | 上游版本、commit 与源码哈希 | 固定可追溯原始基线 |
| `requirements.txt` | 锁定核心依赖 | 建立独立环境，不能任意升级 |

上游是 Transformers v5.3.0，commit `aad13b87ed59f2afcfaebc985f403301887a35fc`。本地适配主要把相对导入改为 `transformers.*` 绝对导入，来源记录声称不改变原架构和参数名。本轮校验两个模型/配置文件的 LF 规范化 SHA256，与记录的 adapted hash 都匹配。

代码明确从本地类导入，不让 AutoModel 悄悄选择上游实现；smoke 中又检查模型、视觉和语言模块的源码位置。这很重要：以后修改了文件，要确保真实推理确实使用它。

依赖固定为 PyTorch 2.10.0、torchvision 0.25.0、Transformers 5.3.0、Accelerate 1.12.0、Pillow 12.1.1。导入模块还会检查 Transformers 恰好是 5.3.0。README 的 Windows/4060 与 CPU 测试环境属于作者的记录，不是已核验的本机或集群环境。

## 3. 原始模型：视频如何变成回答

```text
视频帧与时间信息
    ↓ 处理器：采样、调整尺寸、整理时空 patch、形成模板和位置元数据
视觉输入 + video_grid_thw
    ↓ Qwen3_5VisionPatchEmbed：带时间维度的 patch embedding
视觉 Transformer
    ↓ Qwen3_5VisionPatchMerger：合并空间 patch，投影到语言维度
视觉 embedding
    ↓ 替换文本模板里的 video 占位符 embedding
视觉/文字交错序列 + 多模态位置
    ↓ Qwen3_5TextModel：Gated DeltaNet 与普通注意力交替
    ↓ lm_head：把 hidden state 转为词表 logits
逐 token 生成回答
```

与已有 LLaVA 知识的联系：仍然可以按“视觉编码→对齐语言维度→语言模型回答”理解。变化主要在视频 patch 的时间维度、多模态位置和语言层的混合历史机制。

官方固定权重配置为语言 hidden_size=1024、24 层；视觉 hidden_size=768、12 层，merger 输出 1024。`0.8B` 在模型卡的语言模型条目下列出，不能把它机械当作完整多模态模型及缓存的总显存成本。[固定权重配置](https://huggingface.co/Qwen/Qwen3.5-0.8B/blob/2fc06364715b967f1860aea9cf38778875588b17/config.json)

视觉 patch_size=16、temporal_patch_size=2、spatial_merge_size=2。通俗地说，一个初始视频 patch 不只覆盖一小块空间，还覆盖两帧的对应区域；随后相邻 2×2 空间 patch 合并，减少传给语言模型的 token 数。若处理后尺寸和帧数恰好可整除，语言视觉 token 近似为 `(F/2)*(H/16)*(W/16)/4`。实际数量由处理器的尺寸调整、补帧及 grid 确定，不能直接按原视频尺寸估算。

因此流式片段边界必须处理：第 1 帧单独到达时，等待第 2 帧还是采用明确的补帧策略？重复补同一帧可以做到不读未来，却可能与离线成对处理不一致；它们是不同的输入协议。为了等价性，先固定一种协议，再比较整段与分块。此处是实现建议，仓库尚未指定在线边界策略。

`get_video_features` 复用图像特征入口，visual 使用 grid 组织时空结构；占位符数量与视觉 token 数必须匹配。视频支持并不意味着代码可以对任意新增视频片段直接续接缓存。

## 4. 混合语言架构：两类历史记忆

该 0.8B 配置的 24 层按以下模式重复 6 次：

```text
Gated DeltaNet → FFN
Gated DeltaNet → FFN
Gated DeltaNet → FFN
普通 Gated Attention → FFN
```

共 18 个 linear_attention 层、6 个 full_attention 层。此仓库实现及固定配置对应稠密 FFN，没有用到 MoE 专家路由；不能把整个 Qwen3.5 家族的宣传描述等同于此型号结构。

### 普通注意力：保存可逐条查看的笔记

每个已处理 token 留下 K 和 V，新 token 用 Q 读取历史。它容易保留和访问细节，但笔记长度随输入增长。源码 `Qwen3_5DynamicCache.update` 用 `torch.cat` 追加，当前没有裁剪或上限。

### Gated DeltaNet：持续更新固定大小的记忆矩阵

它把过去逐步融入一个矩阵状态，而不是给每个旧 token 永久保留一份 KV。新信息会影响衰减、写入力度，以及对旧预测的修正。为理解代码，可写成简化更新：

```text
先遗忘部分旧状态 → 用当前 key 读取旧记忆
→ 比较当前 value 和读出的结果 → 写入修正
→ 用当前 query 从新状态读取输出
```

更接近源码的简式（省略归一化、头维度和输出门控）是：

`S_decay = alpha_t * S_prev`

`error = v_t - k_t^T S_decay`

`S_t = S_decay + beta_t * k_t * error^T`

`y_t = q_t^T S_t`

固定状态大小意味着不会因历史越来越长而增加矩阵尺寸，但不意味着可以准确记住无限细节，也不意味着状态只含最近 W 帧。它是学习出来的融合结果，不是人工文字摘要。

短卷积状态保存最近少量 token 的局部特征，帮助当前 token 与相邻 token 混合；它不是“保存最近 4 帧”。卷积核长度为 4，而一帧或一对帧可以对应很多 token。

代码实际保存四类列表：

| 状态字段 | 所属层 | 是否随 token 数线性增长 |
|---|---|---|
| `key_cache` / `value_cache` | 普通注意力 | 是 |
| `conv_states` | Gated DeltaNet 短卷积 | 否，固定尺寸 |
| `recurrent_states` | Gated DeltaNet 递归记忆 | 否，固定尺寸 |

类注释中部分 `ssm_states` 命名是历史措辞，代码实际字段为 `recurrent_states`，修改时以可执行源码为准。

由此带来四个约束：

1. reset 必须清掉四类状态，并管理模型对象上的 `rope_deltas` 及会话元数据。
2. 问答分支必须隔离所有可变状态，不能只复制 KV 后仍共享递归矩阵。
3. 裁掉旧 KV 不会清除递归记忆里的旧视频影响；这是“有长期递归历史的混合记忆”，不能声称严格只看当前滑窗。
4. 递归层尺寸固定，整个模型仍会因 6 层 full_attention 的 KV 增长而占用更多内存。

仅作缓存量级估算：6 个注意力层、2 个 KV heads、head_dim=256，若 K/V 是 BF16，每 token 的 KV 约 `2*6*2*256*2=12288` 字节，即 12 KiB；4096 token 约 48 MiB。18 层递归矩阵每层 `[B,16,128,128]`，B=1 且 FP32 时合计约 18 MiB。实际还包含卷积状态、权重、视觉激活、临时量和可能的问答副本，不能把这些数字当总显存实测。

## 5. 仓库目前证明了什么

README 记录作者在 Windows / Python 3.11.7 / PyTorch 2.10.0 CPU 下三项 unittest 通过。本轮读取并审查了测试，没有重新执行，故保留“仓库记录”证据等级。

| 测试 | 具体操作 | 可以支持的结论 | 尚未支持的结论 |
|---|---|---|---|
| 本地模块与 checkpoint | 检查源码位置；保存上游随机权重后用本地类加载 | 类来源与参数加载关系正确 | 官方 0.8B 真实质量 |
| 文本 logits / cache | 同随机权重对比上游/本地；3 个 token prefill，再续 1 token，与整段比较 | 小配置迁移及单 token 文字续接一致 | 新增多 token 视频 chunk 续接 |
| 图像/视频 logits | 微型合成 patch/grid，一次前向对比上游/本地 | 这组多模态输入的源码迁移一致 | 真实解码、时间戳、长期状态、视频问答效果 |

smoke 脚本目前只有文字/单图参数，无真实视频入口。官方权重 revision 固定为 `2fc06364715b967f1860aea9cf38778875588b17`；默认关闭 thinking、SDPA、CUDA、最多 64 输出 token，单图先缩至不超过 336×336。首次运行会下载权重，当前回合没有运行它。

## 6. 后续真正增量化前必须处理的源码限制

在固定快照的 `Qwen3_5GatedDeltaNet.forward` 中：

- 524–529 行：复用旧递归/卷积状态的分支条件包含 `seq_len == 1`。
- 556–557 行：非单 token 路径会从本次 chunk 重建卷积状态。
- 592–602 行：非单 token 路径传递 `initial_state=None` 给 chunk delta rule。

通俗解释：目前代码支持“整段读入一次，再一个字一个字接着生成”。若之后把一段新视频的几十/几百个 token 一次追加，普通注意力层会接上旧 KV，但递归层走的路径并没有接上旧矩阵和旧卷积历史。

这是明确的源码行为，以及未来视频续接的风险；尚未用真实模型运行证实误差大小。它不说明原始生成基线错误，也不说明算法不可行。现有 3→1 文本测试恰好不覆盖这个问题。

第一项针对性测试应为同一 token 序列的“一次前向 / 3→1 / 2→2 / 1→3”等分法，比较 logits 和各层状态。之后让多 token chunk 显式承接旧递归状态，卷积跨 chunk 也要衔接。逐 token 输入可作低效率参考，不宜作为最终高效视频方案。

多模态位置也有独立问题：`compute_3d_position_ids` 和 generation 针对已有 `rope_deltas` 有续写路径，不能假定这等同于新视频 token 的时间/空间坐标。已有 cache 下追加新视觉内容必须构造并验证 position_ids；缓存数组长度、累计已见 token、真实时间与视觉坐标是不同概念。缓存裁剪后 `get_seq_length` 只返回保留 KV 的长度，不能再把它直接当历史累计位置。

## 7. README 六项计划怎样理解与验收

### 1）验证官方文字、图像、短视频

目的：知道原模型确实能处理我们输入的样例，区分加载问题、感知问题和后来架构问题。
产物：固定权重/依赖、来源检查、真实 token/grid、少量离线预测、GPU 峰值和日志。
顺序：文字→单图→2–4 帧短视频。先通过原始基线再修改缓存。

### 2）视频读取、抽帧、时间戳与滑窗问答

目的：先建立完整视频系统，例如只用最近一小段已到达视频回答“现在发生了什么”。固定 W 帧，接收一帧后丢掉最旧帧，就能控制原始窗口长度。
如果每次重新处理这个窗口，这是在线滑窗基线。它能验证数据流和交互，但尚未完成模型级增量状态改造。
产物：已到达帧队列、实际时间戳、窗口边界、在线采样策略、输入清单；不读取未来帧决定当前样本。
参数 W/FPS/回答频率目前仓库没有定，需要后续用小预算明确，不能把之前的 16 帧硬上限当成合作方已有要求。

### 3）持续输入与可视化演示

目的：视频持续进入，界面显示当前时间、窗口和回答。推荐首版显式按钮/问题触发回答，若以后自动播报再定义触发策略。
演示必须解释答案看到哪个时刻的视频；播放画面、解码时间和模型分析可能不同步。必要时限制队列、说明丢帧策略，不能越积越多。
这仍是系统功能，只有第 5 项才处理真正的模型内部状态续接。

### 4）响应延迟、显存与长期稳定性

目的：测哪里慢、为什么占用上涨，建立优化对照。
应分开测采样/视觉编码/prefill/首 token/生成耗时；显存分 allocated/reserved；记录队列积压和活跃状态字节数。持续循环问答/reset，检查会话串扰和增长。
不要仅报告 demo 跑得动，或用 CPU 测试数字推断 GPU 实时性。

### 5）增量推理、KV 与递归状态优化

目的：只处理新到达的内容，让新帧能读取历史状态，控制全注意力 KV 的长期增长。
至少解决多 token 递归续接、时间 patch 边界、位置续接、容量策略、reset 和问答分支。若裁剪 KV，还要明确“递归历史保留”还是“严格滑窗”的语义，前者与后者验收不同。
产物：append/ask/reset 等增量接口和成对证据；同一输入协议下整段/分块等价、同前缀不同未来、改变早期关键帧、问答后继续视频不污染、内存有界。

### 6）流式数据与 SFT

目的：如果原预训练模型不适应目标在线任务，再训练它在指定时间点回答正确内容。
数据应是“截至 t 的视频 + 问题 + 只依赖 ≤t 内容的答案”。例如第 2 秒只看到人拿起杯子，就不能用第 5 秒把杯子放下后才能知道的答案监督它。
起步以答案 token 计算 loss，视觉/提示等位置屏蔽；哪些层训练、是否 LoRA、是否跨 chunk 反传要由架构需要决定。仓库目前没有数据、trainer、训练配置或预算；SFT 是路线中的计划，实施时先有诊断和预算，不能因换了模型就默认马上训练。

## 8. 一个贯穿例子

假设 0 秒红色方块进入，1 秒移到左侧，2 秒红方块消失、蓝方块进入，3 秒只剩蓝方块。

- 离线模型在 3 秒拿到完整片段，可以答“先红后蓝”。
- 在线滑窗只有最近 2 秒，可能无法看到最早红方块；这是窗口保留范围导致的限制。
- 增量模型已经接收红方块的视觉 token，再接收蓝方块 token，问“最先出现什么”应利用真正历史状态回答。
- 若接入第 2 段时递归历史丢失或 KV 被裁掉，答案可能改变，这正是要用受控对照定位的问题。
- 只看递归矩阵存在不足以证明记忆有效；必须改早期关键帧、保持末帧相同，再看配对回答是否正确变化。
- 新视频开始 reset 后，不能把上一段的红方块带入新回答。

## 9. 我们沿合作方案推进的顺序

保留仓库六项主线；实现前增加必要的状态契约检查，不另起新基座方案。

1. 核验本机/集群并建立独立的固定版本环境，留原模型只读基线。
2. 重跑仓库三个小测试，增加多 token 缓存续接测试，以低成本发现结构问题。
3. 官方权重文字/单图/短视频验证，取得实际输入/输出和成本证据。
4. 在线采样、滑窗问答和可视化，建立可解释系统基线。
5. 分阶段实现混合状态增量化与有界 KV 策略，逐项验证，不同时改数据、训练和记忆压缩。
6. 若能力证据表明需要，构建前缀 QA 并做小规模 SFT。

本轮只审阅并建立文档/快照；未修改合作仓库、未推送、未下载权重、未提交 GPU 作业。
