# 空间选择、排列与匹配时间标签：固定案例结果

这是2026-10-14本阶段的固定结果快照，持续进度以《实验总纲.md》为准。本阶段没有修改默认模型核心或综合汇报，没有训练。目的不是扩大测试数量，而是解释：为什么旧猫的完整特征能读出深色，减到48个Token后有些方案却答浅色？

## 为什么需要这轮实验

上轮已经发现：不做平均，仅保留融合算法留下的原始目的Token，仍然答错。因此，不能简单说“平均把毛色抹掉了”。但完整首对的时间标签不同、排列和位置不同，也不能马上说只因选错了Token。

这次把这些因素分开。仍使用同一段旧猫视频的0—3秒四帧，以及两张上一轮已经使用的深色猫、浅色猫照片。照片各重复四次，不是新视频或留出测试。

## 我们改了什么

新增独立诊断目录 `diagnostics/selection_layout_v1`，没有把任何候选设为默认。两对画面经视觉编码后，各有48个、共96个1024维投影Token。每对的空间网格是6×8。

比较六种48Token方案：

| 方案 | 保留下来的东西 | 空间覆盖 |
|---|---|---|
| 完整首对 | 第一对的全部48个原始Token | 一份完整6×8网格 |
| 完整末对 | 第二对的全部48个原始Token | 一份完整6×8网格 |
| 奇数列 | 两对各取第1、3、5、7列，列号从0开始 | 24个格子各来自两对 |
| 偶数列 | 两对各取第0、2、4、6列 | 另外24个格子各来自两对 |
| 互补棋盘格 | 第一对取半个棋盘，第二对取另一半 | 48个格子各取一次 |
| 原融合 | 原ToMe方案将96个Token融合到48个 | 携带幸存目的Token坐标 |

棋盘格没有查看问题、标签或特征值；它只按固定几何规则选择：

```python
mask = (row + col + source_pair) % 2 == 0
```

它是减少保留Token的诊断候选，没有训练一个新的压缩网络，也没有恢复被删除的细节。只有两对画面都到达后才执行。

每种方案又分别测试两种应用位置：真实来源坐标、统一首个6×8网格。后者是人为位置干预，不改原始来源记录。共同诊断提示显示`<0.0-3.0 seconds>`，不声称每个方案都完整保留了这四秒；首对实际范围仍是0—1秒，末对仍是2—3秒。

六种方案按空间位置排列；另外保留原来按时间排列的奇数列和融合方案，检查重排是否影响结论。再加96Token完整参考、真实0—1秒标签的首对，共16组。每组问毛色与主体，两题×三例×16组，共96次真实问答。

关键代码在`selection_reader.py`：`variants()`负责几何选择、独立张量和排列；`context()`负责共同时间窗口与两种应用位置；`answer()`使用独立问答上下文，结束后释放缓存、恢复RoPE状态。

## 有什么效果

旧运动猫的人工真值是深色、猫。下表合并了结果相同的组，原始96条回答全部保存，没有删掉失败：

| 输入 | 毛色回答 | 主体回答 | 这轮能说明什么 |
|---|---|---|---|
| 完整96 | 深色✓ | 猫✓ | 未压缩时本例可答 |
| 完整首48：实际或共同时间标签 | 深色✓ | 猫✓ | 单个标签Token变化没有解释这次退化 |
| 完整末48：两种应用位置 | 深色✓ | 狗✗ | 保住毛色不代表主体也一定正确 |
| 奇数列48：两种位置、两种排列 | 浅色✗ | 猫✓ | 不平均也会丢失本题可读性，重排未修复 |
| 偶数列48：两种应用位置 | 深色✓ | 猫✓ | 同样48个Token，换保留内容后本题恢复 |
| 互补棋盘格48：两种应用位置 | 深色✓ | 猫✓ | 另一个固定、问题无关选择也保留了本题可读性 |
| 原融合48：两种位置、两种排列 | 浅色✗ | 猫✓ | 当前融合失败仍复现 |

两张已见照片在16组中均区分深/浅且回答猫，共64次相关控制正确。这不能当成64个独立样本，更不能当成自然视频泛化准确率。全部96条中88条符合这两个固定标签，也只用于核对结果完整性，不作为项目准确率。

可以把Token想成画面的信息卡片。两组都留下48张卡片，仍可能留下不同信息。本例支持“保留哪些信息值得优先研究”，而不是“只要数量够就能读出来”。同时，偶数列与奇数列都只覆盖24种空间格子，却有不同结果，所以不能把收益单独归因于覆盖格子更多。棋盘格也改变了时间采样；视觉特征含上下文，不能把一格简单理解成只记录那一小块像素。

## 对照是否成立

CPU两项契约通过，并完成随机小模型的6次视觉、96次问答重放。随机输出不做能力评分。131个源码文件在运行前冻结，真实GPU使用相同像素、来源SHA、模型清单和输入布局。

独立审计核验了：

- 完整首对实际标签和共同标签之间，视觉值及全部位置相同，仅一个文字Token不同；本例两者都答对。
- 统一网格下六种48Token方案的文字、长度和全部应用位置相同，差异在所选及排列后的视觉值。
- 每种方案在来源坐标与统一网格之间，视觉值和文字相同；位置干预不改来源元数据。
- 四个冻结参考组与GPU91的输入ID、位置、视觉值SHA和生成ID全部相同。
- 主视频状态、外部节点和所选特征未被问答修改；问答未重新做视觉编码。
- 两种排列共同改变视觉值及其位置的序列顺序，不能包装成只改RoPE的实验。

因此，我们可以收紧本例的解释：一个时间文字Token、测试的两种位置方案以及空间重排，都没有修复奇数列/融合的毛色错误；更换保留的视觉值可以让本题恢复。尚不能证明所有位置策略无关，也不能证明这是一套可靠通用压缩算法。

## 资源与复现

真实GPU92仅载入一次：6次视觉前向、96次问答、367次语言前向、262个生成Token，全部EOS结束；含载入约26.95秒。FP32 IEEE/math、原GDN64、主上下文256、问答512、每答最多24Token，没有改权重。

峰值allocated约3.262GiB；reserved约3.582GiB。RGB画布1,769,472B；外部节点按张量大小保守相加3,958,656B（共享引用可能重复计数），额外复制、投影与匹配暂存估计合计10,594,048B，小于登记16MiB。后者是保守工程估算，不是实测进程RSS。主缓存23,470,080B、指纹临时2MiB另计；照片解码保守预算24MiB。

原RAM≥3GiB、GPU空闲≥5.5GiB、FP32转换余量≥2GiB门禁保持。加载前RAM约4.15GiB/GPU空闲约6.93GiB，360秒watchdog正常返回。

## 反思与下一步

这轮完成了一个有解释力的小结：错误不只是“平均造成的”，同预算下的保留策略确实能改变这个可答细节。它解决的是第一层96→48的局部读取问题，尚未证明更深事件森林、更长视频或历史检索收益。

下一阶段宜冻结棋盘格规则，在未用于挑选规则的多个运动片段上，同预算比较完整参考、首对代表、原融合与棋盘格。先筛清未压缩本身能答的事实，但保留全部基础失败；同时看主体、属性和顺序，避免只修毛色却伤害动作。若局部收益能复现，再单独接入森林一次合并，检查是否在之后合并中消失。暂不把偶数列设为默认，也不同时增加检索、训练和新压缩器。
