# 32计算块候选：交错顺序与多输入结果

2026-10-10固定实验快照，持续进度仅见《实验总纲》。CPU预检及真实GPU均完成，五组输入的全部严格数值对照通过。32块在本机FP32后备实现中，比64块更快；现在有了比先前单例、固定先后顺序更充分的证据。原默认64保持不变。

这里的“32”是语言模型内部一次组织计算的Token数量，不是把视频减少到32帧，也没有丢掉历史。可以把它理解为同一份作业改用较小的计算批次：先检查答案和记忆是否保持一致，再比较耗时。

## 怎样保证比较公平

使用三个精确长度的合成文本，以及四帧洗手、六帧猫视频。视频都使用既有固定时间单元视觉候选，两个计算模式共用同一份真实特征。它们与原模型完整视觉的差别没有在本实验中消失，也没有重新定义原默认路径。

每组每模式一次预热，不计入正式统计；随后六轮正式测量，64先运行和32先运行各三轮。每轮都从空状态分别计算完整前缀、按既定布局增量续接，检查32完整输出对64完整输出，以及两模式的增量输出对自身完整参考。完整对照覆盖全部Token的logits和四类最终缓存；增量对照覆盖最后新增块的logits和全部最终缓存。

五组预热另检查问题后缀、预定HANDS首Token及分支最终缓存的跨模式一致性。十个问答分支均未改变主状态，缓存存储独立，全部拥有的状态reset为空。本轮没有生成答案，预定Token不计回答正确率。

CPU和GPU分别包含35轮、115项数值对照，其中正式计时30轮；这是固定输入重复验证，不能当成115道独立能力题。沿用logits最大误差≤0.01、平均≤0.0001、RMS≤0.0003，并同时要求allclose(atol=rtol=1e-4)；四类缓存也全部要求allclose1e-4。没有放宽门槛。

## 实测速度

下表是正式六轮的墙钟中位数，包含语言模型与输出头；分段累计是同一前缀所有增量调用耗时之和。“减少”使用每轮32/64配对比值的中位数，计算方法不同于直接相除两列中位数，保留逐轮比值与两种先后顺序的统计。

| 输入 / Token数 | 完整64→32（ms） | 完整耗时减少 | 分段累计64→32（ms） | 分段耗时减少 |
|---|---:|---:|---:|---:|
| 合成文本 / 31 | 132.24 → 93.08 | 31.2% | 258.17 → 174.95 | 30.2% |
| 合成文本 / 65 | 144.81 → 107.61 | 23.7% | 394.17 → 270.46 | 30.9% |
| 合成文本 / 129 | 153.86 → 121.57 | 19.9% | 514.41 → 349.83 | 29.6% |
| 洗手四帧 / 115 | 153.61 → 111.13 | 26.5% | 405.96 → 275.91 | 33.8% |
| 猫六帧 / 171 | 151.93 → 125.10 | 17.4% | 502.64 → 370.32 | 26.8% |

两种顺序分别计算的中位数均显示32更快。本轮所有五组×六轮的完整/增量配对比值也均小于1，但波动仍存在：例如129Token分段比值，两顺序中位数约0.636和0.757。只有一台设备、一次真实载入、两种视频画面，六次计时不足以证明所有输入或硬件都有同样收益。

即使用32，分段累计仍高于一次完整计算。这符合增量输入需要多次启动模型的成本；分段的价值是持续接收新画面、复用此前历史，不能因此宣称短视频全部处理更快。本实验没有测解码、视觉、触发等待和答案生成组成的端到端延迟，也没有证明摄像头长期实时能力。

## 数值、内存和清理

五组所有数值门槛通过。各组全部控制中最大的logits绝对差分别约2.81e-5、3.53e-5、7.51e-5、9.82e-5、1.10e-4；四类缓存最大绝对差分别约2.38e-5、4.58e-5、2.17e-5、3.43e-5、3.91e-5。猫组单一最大差略大于1e-4，但allclose同时含相对容差，且另三项误差门槛全部满足；这不是放宽绝对容差或逐位一致性证明。

实际2次视觉编码、250次候选内部Linear投影、314次语言前向、5472次多Token GDN包装调用；单Token递归路径未改，生成0。单次模型载入，43.090秒含加载，未触发600秒看门狗。载入前资源门槛通过，没有集群作业或训练。

CUDA allocated峰值4.608GiB，reserved峰值6.201GiB；二者分别是实际分配和分配器预留，不能把后者省略。单组额外视觉特征最大589,824字节（576KiB），低于8MiB硬限；逐轮释放大logits/状态，不保存Tensor、权重或素材副本。

钩子、方法和计算包装均恢复。删除模型变量并清理后，子进程内仍有9.125MiB allocated、22MiB reserved，原因未定位；进程退出后一次驱动查询used=0MiB，free=7957MiB。首次审计误设“进程内立即归零”断言失败，失败快照和说明保留；修正审计仅记录真实残留并核验退出后释放，未重跑推理或修改冻结实验。

第二次交付审计通过：两运行的冻结方案/启动器/代码/输入和真实10模型资产、两素材SHA；旧60源文件及原15参考文件不变，新增一个独立实验模块，当前61源文件。八种篡改证明均在创建GPU运行目录、日志和载入前拒绝。成功运行的重复partial先证明被最终报告完整覆盖后删除，只清理本轮可再生字节码；旧失败记录保留。

## 下一步的建议

32候选值得进入显式可配置接口：保留64默认，通过实验选项选择32，统一限制当前torch后备实现，并保证异常恢复。随后在既有短视频问答原型中做一次预算明确的回归，检查位置、四种历史状态、回答分支、reset、生成和整条问答延迟，再判断是否作为本机FP32演示选项。当前实验没有完成这项接口接入。

BF16数值问题、原模型早期画面/顺序/数量反例、真实长期输入仍未解决。32不会自动修复这些能力问题；KV已经使用，Token压缩和记忆森林继续等待明确的长历史需求与基线证据。Git协作仍需核验用户提交身份和远端写权限，在个人分支经PR合并main，未推送。
