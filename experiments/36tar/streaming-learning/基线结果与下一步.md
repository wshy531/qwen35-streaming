# Qwen3.5-0.8B 原模型最小基线：证据报告

实验日期：2026-10-09。本文件固定本轮结果；持续进度与下一阶段是否启动只看 `实验总纲.md`。

## 本轮结论

原模型文字、单图和三条短视频的小规模离线推理均得到预期答案。原仓库模型、配置、测试等 15 个来源文件在工作副本中与只读快照逐字节相同；没有训练、Token 压缩或记忆森林。视频为兼容固定版 Transformers 的已知位置接口问题，使用显式 position_ids 输入适配，必须与完全无适配基线区别报告。

这建立了可继续学习的最小起点，不证明模型已经具有持续流式输入、长期记忆、自然视频可靠理解或实时性能。

## 实际预测和资源

样例为自生成的白底色块：单图 256×256；视频同尺寸、1 FPS、4 帧，每个颜色连续两帧。所有视频问题相同：“视频开头方块是什么颜色？用一个英文颜色词回答。”完整 4 帧一次进入模型，问题没有给出目标颜色。

| 输入 | 预期 / 实际答案（去除空白） | 输入 / 输出 Token | generation 秒 | allocated / reserved 峰值 GiB |
|---|---|---|---:|---:|
| 2+2 | 4 / 4 | 25 / 4 | 1.008 | 1.653 / 1.729 |
| 红色方块图片 | red / red | 91 / 4 | 0.455 | 1.663 / 1.754 |
| 红、红、蓝、蓝 | red / red | 175 / 4 | 0.683 | 1.674 / 1.730 |
| 绿、绿、蓝、蓝 | green / green | 175 / 4 | 0.263 | 1.674 / 1.742 |
| 蓝、蓝、红、红 | blue / blue | 175 / 4 | 0.282 | 1.674 / 1.742 |

generation 包含视觉前向、语言 prefill 与 decode，不含前面的 CPU 解码/处理、传输和输入位置适配；不是单独首 Token 延迟。文字/图片与视频来自两次运行，各次首例有初始化影响；没有统一预热、重复采样或统计误差，因此不比较模态加速比，也不据此承诺实时 FPS。GPU allocated/reserved 是 PyTorch 分配器统计，不等同系统显示的全部显存。

配对解释：红→蓝和绿→蓝的末帧相同，答案分别为 red/green；蓝→红的回答仍是 blue。这排除了在这些样例上只根据末帧颜色作答的解释，但不是长期记忆证据。只有三条视频，不能称为基准准确率，也未验证完整事件顺序描述。JSON 中 contains_expected 是辅助文本检索，表中结论依据实际完整答案检查。

## 输入路径如何理解

```mermaid
flowchart LR
    A[真实 MP4 解码出 4 帧] --> B[处理器：时间戳、两帧时间块、空间 patch]
    B --> C[视觉编码：2 个时间块，每块 64 个视觉 Token]
    C --> D[128 视觉 Token 加提示文字，共 175 Token]
    D --> E[24 层混合语言模型：18 DeltaNet 加 6 普通注意力]
    E --> F[使用原生缓存生成答案]
```

实际 video_grid_thw 为 `[2,16,16]`，spatial_merge_size=2，因此视觉 Token 数为 `2×16×16÷4=128`。单图 grid 为 `[1,16,16]`，对应 64 Token。视频的 T=2 是两个时间 patch，不是模型只读取了两张原图；解码实际读取 4 帧。

## 首轮失败与兼容适配

首次 GPU 运行先完成文字和图片，随后视频在 `get_rope_index` 发生 StopIteration，尚未进入视频模型前向。处理器把视频拆成由时间戳隔开的两组视觉 Token，但固定版位置构造器只拿到一行 `[2,16,16]`，无法逐组消费 grid。

上游已合并的 [Transformers PR 44474](https://github.com/huggingface/transformers/pull/44474/files) 对应修复是在位置计算时把视频 grid 按时间拆分。我们保留版本与原模型文件，新增明确的 `--repair-video-positions` 开关：仅调用原位置构造器时传两行 `[1,16,16]`，得到 3 轴视觉位置，再加一轴顺序位置形成 `[4,1,175]`；视觉编码器仍接收原 `[2,16,16]` 与全部像素。这是输入兼容处理，没有改变视觉特征预算、模型权重或缓存算法。

适配目前只支持 batch=1、无 padding 的独立离线样例，不直接用于流式续接、混合图像视频 batch 或已存在 past 的会话。每例清除模型对象 rope_deltas，再根据当前输入重建；不让上一例的位置状态进入下一例。

CPU 验证包括：实际三条视频逐坐标与独立手算 oracle 完全相同；随机小模型的双时间块视频，本地/上游 logits 最大误差 0；显式四轴位置连续生成 3 Token 正常。实际 GPU 三条视频再验证整个路径能完成。原失败日志和原始预测完整保留，未改写为成功。

## 缓存诊断：后续最值得研究的点

原仓库三项随机小模型测试全部通过，包含来源、保存重载、文字/图像/视频本地与上游对照，以及 3 Token 前缀后追加 1 Token。

我们另用相同的 4 个文字 Token 比较整段前向和不同切块：

| 切块 | 最大 logits 绝对差 | 在 atol=1e-5、rtol=1e-4 下 |
|---|---:|---|
| 3→1 | 5.96e-8 | 一致 |
| 逐 Token：1→1→1→1 | 7.45e-8 | 一致 |
| 2→2 | 0.003971 | 不一致 |
| 1→3 | 0.004302 | 不一致 |

源码中 GatedDeltaNet 有缓存时仅在 seq_len=1 的分支复用历史；多 Token 分支重建卷积状态、递归 initial_state=None。实验与这一风险一致。这里是随机小模型数值诊断，尚未在官方权重上测量能力影响，不能当作原模型“视频答错”。普通生成一次追加一个 Token，所以本轮正确生成和未来多 Token 视频块续接不一致并不矛盾。

因此直接把新增一批视觉 Token 和 past_key_values 一起送入原模型，还不足以宣称已实现增量。后续需同时处理 KV、卷积、递归状态和位置，先做整段/分块等价，之后才讨论压缩。
