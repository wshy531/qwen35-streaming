## 为什么需要它、这次改了什么

此前的读取诊断证明，选出相关旧节点可以恢复固定样例中的毛色回答，但仍是实验脚本。这次增加`diagnostics/time_file_v1`，把已有混合状态主会话、成功写入后的投影捕获、完整帧对时间索引和独立历史问答组合成可用文件入口。

| 部件 | 作用 |
|---|---|
| `file_session.py` | 新帧先写主会话；成功形成帧对后才提交时间索引；管理有界预览与查询隔离 |
| `file_demo.py` | 文件采样、参数检查、查询/重置日程、终端事件、离线HTML、CPU与GPU门禁 |
| `contracts.py` | 连续输入、淘汰、失败不提交、跨reset、孤帧、拒绝、边界、报告与未达触发点检查 |
| `dependencies.py` | 复用冻结的模型/捕获/索引/读取实现，默认源码保持 |
| `run_demo.py` | 导入前冻结本段源码、独立运行目录、360秒watchdog |

默认保留最近3个完整帧对，每对48个1024维FP32投影Token。满后淘汰最早一对。索引在CPU上保存特征，历史问答复用这些特征，在新的语言上下文生成；**不会重新编码预览JPEG**。

为复用已验证的捕获器，内部旧`EventRuntime`仍有自己的有界银行。这份状态与额外索引、临时副本均计入资源估计，不能把时间索引的144Token当作整个系统全部状态。主KV/卷积/递归状态与外部索引分别管理。

预览最多保留与当前索引对应的3对JPEG，加一个待配对帧的展示信息。曾成功查询过的预览会另存到本轮报告目录，便于回看；这些磁盘图片**不参与后续检索**。所以即使旧报告图片还在，当前索引淘汰后仍会拒绝该时间的问题。

## 怎样运行

以下PowerShell示例复现本次13次请求。两个阶段必须使用相同配置；输出目录必须全新。

```powershell
$py = 'E:\VIT Model\.venv\Scripts\python.exe'
$entry = 'E:\VIT Model\publish\qwen35-streaming\experiments\36tar\streaming-learning\diagnostics\time_file_v1\run_demo.py'
$plan = 'E:\VIT Model\publish\qwen35-streaming\experiments\36tar\streaming-learning\diagnostics\time_file_v1\acceptance_plan.json'
$common = @(
  '--model-dir', 'E:\VIT Model\models\Qwen3.5-0.8B',
  '--video', 'E:\VIT Model\datasets\natural_commons_v1\cat_play.webm',
  '--fps', '1', '--duration', '12', '--max-frames', '9',
  '--max-pairs', '3', '--reset-after-pairs', '1', '3',
  '--query-plan', $plan, '--branch', '36tar/general-video-demo'
)
& $py $entry --stage preflight @common --out 'E:\VIT Model\runs\my_time_file_cpu'
& $py $entry --stage gpu @common --preflight 'E:\VIT Model\runs\my_time_file_cpu' --out 'E:\VIT Model\runs\my_time_file_gpu'
```

可替换`--video`路径、`--fps`、`--duration`、`--max-frames`和问题计划。合作方使用自己的当前分支填写`--branch`；入口不写死36tar个人分支，但GPU禁止在main/master/游离HEAD运行。

问题计划是JSON列表，例如：

```json
[
  {"after_pairs": 1, "question": "Name the animal visible at 0.5 seconds."},
  {"after_pairs": 3, "question": "Name the animal visible at 0.5 seconds."},
  {"after_pairs": "eof", "question": "Name the animal visible at 2.5 seconds."}
]
```

也可不用`--query-plan`，改用一个或多个`--question`，在本轮处理结束后查询。`eof`表示本次处理结束，可能因为文件自然结束，也可能因为帧数/时长上限。尚未到达的数值触发点会保留为`pending_unreached`，不会挪到结束时偷偷补问。

这是运行前预设问题的文件入口，尚无运行中键盘聊天；也不按墙钟播放，不打开摄像头。默认入口保持原样，本模块需要显式运行。

## 支持范围和资源限额

当前严格时间查询仅支持两种精确英文模板，T填写非负十进制秒数：

```text
Name the animal visible at 0.5 seconds.
Is the animal's coat mostly light-colored or mostly dark-colored at 0.5 seconds? Answer light or dark.
```

问题时间按文件首帧归一化PTS解释，不是人为拼成整数秒的合成视频标签。证据保留解码帧ID和归一化文件时间。0.5秒查询取覆盖0—1秒的采样帧对，不代表存在一张第0.5秒的精确画面。

适配层对帧对边界只使用`1e-9`秒绝对容差，处理文件把1秒表达为`0.9999999999999999`的浮点误差；原始时间原样记录。它不会跨过实际帧对空隙去找最近画面。这个新增边界分支由CPU组件契约验证，最终GPU沿原13请求验收，没有把mock结果冒充新GPU回答。

本学习入口限制视频≤64MiB、采样0.1—4FPS、时长≤60秒、帧数2—32、索引1—3对、每次最多24个预设请求。主预算256—512Token、独立QA768、每答最多24Token。任一配置GPU运行前，都需要该配置的新鲜CPU证明与同一源/模型/视频/计划SHA。

不支持或歧义问句、尚未编码/空索引、早于当前保留范围、帧对间空隙会有结构化拒绝。它检查的是语法与证据时间覆盖，**不检查取回画面是否真含有问题所问对象**，也不是任意语义检索。

## 本次真实验收效果

最终GPU98使用已知猫视频，9个真实采样帧形成4对，最后8秒的单帧不补成新对；成功编码范围到7秒。主状态在第1、3对之后显式清空。13次请求中6次调用模型、7次拒绝，拒绝时语言前向为0。

| 时点/请求 | 实际行为 |
|---|---|
| 输入前问0.5秒 | 无完整帧对，拒绝 |
| 第1对后清主状态，问0.5秒 | 取回0—约1秒，回答猫 |
| 仅第1对时问2.5秒 | 尚未编码，拒绝 |
| 第2对后问2.5秒 | 取回2—3秒；模型误答狗 |
| 第2对后问0.5秒毛色 | 取回首对，回答深色 |
| 第3对后再次清主状态，问0.5秒 | 仍取回首对；生成ID与前次逐位一致 |
| 第4对后问0.5秒 | 索引只剩第1/2/3号对，旧首对已不在保留范围，拒绝 |
| 第4对后问4.5秒 | 取回4—5秒；模型误答狗 |
| 问5.5秒 | 位于两对之间的空隙，拒绝 |
| 问9.5秒、结束后问8.5秒 | 超过成功编码范围，拒绝；8秒虽收到，但未成对 |
| 结束后问6.5秒 | 取回6—7秒；模型误答狗 |
| 问“What happened?” | 不属于当前模板，拒绝 |

机制验收通过：持续输入、成功写入才提交、外存跨主reset、只读查询、淘汰、真实孤帧与拒绝路径都有实际证据。

模型理解仍有明显错误：六次回答中，首对两次“猫”和一次“深色”符合标签，另三对猫被答成狗。这些是同一视频中的相关检查，不是通用准确率。本段改善的是读取入口和可观察性，没有证明基础识别变强。
